# specgo — 规格化全链路编排（主流程）

新功能从需求到交付的唯一编排入口。主代理不亲自分析、设计、编码——只做流程推进、用户确认、子代理派发与验收。

## 分工原则

| 角色 | 职责 |
|---|---|
| 主代理 | 步骤推进与衔接；所有与用户的询问/确认；派发子代理（prompt 含 skill 加载指令+输入+产出+返回要求）；验收子代理产出；每步末组织 ask-human 审视门；汇总报告 |
| 子代理 | 干活：资产分析、建模审核、story 撰写、代码实现与测试、代码检查与修复。每个子代理**第一步必须加载对应 skill 全文**再开工 |

**用户交互中转模式**：子代理执行中遇到需要用户输入的点（断点补齐、疑问澄清、修复决策），不得自行脑补——返回"待确认清单"结束本轮；主代理向用户询问后，把答案回传**同一子代理**（task_id 续会话）继续，不新起子代理重做。

## 固定 ask-human 审视门（最高纪律）

**每个步骤的校验环节结束，固定进入 ask-human 审视门——无一例外：**

1. 主代理列出本步**新生成/修改的全部文档与代码清单**（逐条带路径），附验收结论（mermaid VALID 结果、测试/构建命令结果、待确认项闭环情况），用 AskUserQuestion 询问用户是否审视通过。
2. 用户审视通过 → 才允许进下一步；用户有意见 → 主代理把意见回传对应子代理（task_id 续会话）整改，整改后**重新过同一道门**。
3. 尤其任何**新生成文档**（资产文档、建模 HTML、story、刷新后的资产文档、全链路分析报告）必须经人审视后才允许继续执行——子代理自验 VALID/通过不等于门通过，主代理验收通过也不等于门通过。
4. 不默认、不跳过、不替用户回答；用户明确要求"后面都别问了"时，在最终报告中注明被跳过的门。

## 第 1 步：资产检查与录入/刷新

1. 探测四类核心资产目录：`docs/` 下——`0-biz/interface/`、`0-tech/framework-guidelines/`、`0-tech/external-call-guidelines/`、`0-arch/structure-model/`（README.md 仓级总览 + structure-model-*.md）。
   - 需要全套 14 类资产（含 object-model/data-model 等）时，改派 spec-analyze 子代理做一键全量分析，本步后续小步跳过。
   - `docs/business/` 旧体系资产目录（story/key-class/data-structure 等）如存在仅作"外部文档引用"素材，不再探测录入（对应旧分析 skill 已删除）。
2. 分支：
   - **存在** → 询问用户是否需要刷新资产
   - **不存在** → 询问用户是否需要录入资产
   - **选否** → 跳过本步；后续步骤的"外部文档引用"章节按"无引用"处理
3. **选是** → 同一条消息**并行**派发 4 个子代理，每个加载一个分析 skill 全文后执行（可让用户勾选子集，默认全量）：
   - structure → arch-structure-model-analyze
   - interface → biz-interface-analyze
   - external-call-guidelines → tech-external-call-guidelines-analyze
   - framework-guidelines → tech-framework-guidelines-analyze
4. 验收：产出文档落位对应目录（正式或 `_review/`）；含 mermaid 的文档全部通过 mermaid-validate 验证脚本（VALID）。
5. **审视门**：列出本步新生成/刷新的资产文档清单（带路径）+ VALID 结论 + `_review/` 待审清单，ask-human 审视通过后才进第 2 步。

> 注：交互模型文档（docs/0-arch/interaction-model/interaction-model-*.md）不属于本步自动检查的资产——它由用户主动指定流程后经 arch-interaction-model-analyze 提取产出，不派全量子代理。

## 第 2 步：需求与功能审核（spec-function-design-audit）

- 派**审核子代理**：加载 spec-function-design-audit 全文执行（需求/功能设计审核），输入=需求/SR/功能设计文档，完成多彩建模翻译 + 全面扫描（表述质量/逻辑断点/设计要素）+ HTML 初版。
- 子代理返回合并断点清单；**主代理**批量抛出全部问题 ask-human（每问给 2-4 个候选答案+推荐项），用户批量回答后核对——未答/含糊/引入新疑点的继续批量追问，无新问题的答案回传子代理补齐，直至建模闭环、HTML 定稿。
- 审核通过后按 skill 阶段 6 询问用户是否输出规范功能实现设计 md。
- **审视门**：建模闭环后，列出定稿 HTML（及可选的规范功能设计 md）路径，ask-human 审视通过后才进第 3 步。
- 用户明确说"需求已确认、不用审核"时可跳过，并在最终报告中注明。

## 第 3 步：story 设计（spec-story-design）

- 派**设计子代理**：加载 spec-story-design 全文，输入=第 2 步审核通过的 Spec + 第 1 步资产文档（framework-guidelines 框架指导 + docs/1-storys 既有 story 为参照）。
- 产出 `docs/1-storys/{功能名}/{功能名}-story.md` **单一文档**（合并功能澄清 + 代码实现指引，不产出独立 develop-task.md）。
- 子代理在第 5.2 步返回疑问清单 → 主代理批量向用户澄清 → 回传子代理定稿。
- 主代理验收：story 模块设计完整（变更条目写清更改对象与内容）、功能点修改清单到函数级、mermaid 全部 VALID。
- **无审视门**：story 设计完成后**自动连续进入**第 3.5 步人话改稿 → 第 3.6 步功能点判读，中途不 ask-human（首次生成 story 后自动执行判定，3~3.6 为一个完整闭环）。

## 第 3.5 步：人话改稿（spec-humanize）

story.md 产出后**自动执行**（不 ask-human），派**改稿子代理**：加载 spec-humanize 全文，输入=第 3 步定稿的 story.md。

- 改写正文散文段落去 AI 味（写人话/禁翻案腔/禁冒号提示句/禁破折号/禁模型路标/禁商业黑话/长句带主语/阿拉伯数字/技术术语配人话）。
- **只改正文段落与表格内文字**，不动 mermaid 代码块、推导表判定列、文件/代码路径、资产文档引用路径、表格结构、编号。
- 跑 `check_prose.py` 确定性门禁兜底，failures 必清零；未清零回传改稿子代理整改重跑，循环直至 failures=0；warnings 逐条判断（技术引用冒号可保留，提示句冒号必须改）。
- **门禁门**：check_prose.py 结果 failures=0 方放行进第 3.6 步（确定性门禁，不另起 ask-human）。

## 第 3.6 步：功能点判读循环（spec-point-verify）

story.md 推导表判定列「待判读」→ 代码实现前，逐功能点判读推导链并循环闭环，直至全部「通过」才放行。**本步在第 3.5 步人话改稿通过后自动执行，不 ask-human 后才启动。**

1. **派发前主代理做仓内资产对表**：Glob `docs/0-*/*.md` 列出仓内资产文档，按必参考类型归类，把实际文档名清单塞进子代理 prompt。
2. **派判读子代理**：加载 spec-point-verify 全文，逐功能点独立判读推导链是否成立、资产引用是否真实且支撑、业务意图是否覆盖、实现场景必参考文档是否齐全，并做一次跨功能点整体走查（执行顺序自洽、校验先后合理、错误语义一致、编码必需信息齐备）；另跑影响面 grep 扫描防漏行。
3. 子代理返回判定结果（三档：通过 / 需修订 / 打回设计）+ 人话理由 + 偏差清单，回填同一份 story.md 推导表判定列原位置（不另起文档）。
4. **循环闭环**（有「需修订」或「打回设计」时），判读子代理对每个需修订项先分类：
   - **可推理自修订**（通过代码/文档事实可推导出正确答案，如 ALTER TABLE 缺失、遗漏函数删除导致编译断裂等）→ **判读子代理自行修订 story.md 推导表原位置**，不 ask-human，修订后重判该功能点；
   - **需人工决策**（genuinely ambiguous，如方案 A/B/C 选择、业务策略取舍等，无法通过代码/文档推理得出唯一答案）→ 返回待确认清单给主代理，主代理批量 ask-human 澄清，收到答案后回传判读子代理修订 story.md 推导表原位置；
   - **打回设计**（推导严重不成立或大量漏引）→ 打回 spec-story-design 第 5 步重写后重判。
5. **闭环条件**：全部功能点「通过」（0 需修订、0 打回设计）**且全部待确认项已闭环**（确认的已回填到推导表/澄清Q&A、留到实现时的已在推导表标注）。未闭环时循环修复直至闭环，不中途放行。
6. 重新派 spec-point-verify 子代理重判修订的功能点（含整体走查复核），回到步骤 3（循环）。
7. 全部「通过」+ 全部待确认项闭环 → 放行。
8. **审视门**：列出 story.md 最终状态（功能点总数、全部通过、影响面 grep 全覆盖、mermaid VALID、check_prose.py failures=0）+ 需关注事项 + 资产缺口汇总，ask-human 审视通过后才进第 4 步。

## 第 4 步：代码实现与测试（spec-code-generate 调度）

**先询问用户**：设计已定稿、人话改稿与功能点判读均通过，是否直接开始实现代码？选否 → 停在本步，输出阶段总结。

选是 → 加载 spec-code-generate 全文，按其角色分工执行：

- 铁律一：**完整代码零 TODO**——任何 TODO/占位符/省略式留空都是交付红线，写不出完整实现就返回待确认清单；
- 铁律二：**子代理只实现代码，可并行多个**——主代理评估实现规模，修改文件清单可拆为互不依赖的文件组时同一条消息并行派发多个实现子代理（按文件分组，组间有依赖严格串行）；测试代码由实现子代理一并编写；
- **主代理执行测试与后续流程**——子代理职责到"代码写完"为止；主代理组装产出、复核零 TODO（实跑搜索命中数=0）、实跑单测（到测试函数级）与集成/E2E 测试（到用例步骤级，仓内有就必须主动跑）、运行 story 验证命令，失败打回实现子代理修复重跑。

汇总返回 spec-code-generate 规定的返回格式：生成/修改文件清单 + 冲突偏差 + 零 TODO 自检结果 + 验证命令结果（DT 到测试函数级）+ 集成测试结果（到用例步骤级）+ 实际加载的文档清单（供第 6 步报告取证）。

**审视门**：主代理汇总代码变更摘要（git diff 文件清单 + 函数级改动概述）、零 TODO 自检结果、单测/集成测试与验证命令结果，ask-human 审视代码实现，通过后才进第 5 步；有意见回传实现子代理整改后重新过门。

## 第 5 步：资产刷新（spec-update）

1. 前置：本需求代码变更已就绪。spec-update 以 git 对比为输入——代码已 commit 时基线最清晰；未 commit 也可基于工作区 diff 执行。**是否提交代码由用户决定，不得主动提交**。
2. 派**资产子代理**：加载 spec-update 全文，基于 diff 识别变更映射到各资产要素的受影响情况，产出刷新清单（受影响/不受影响/资产未建三态判定 + 依据）。
3. 子代理返回刷新清单；**主代理交用户审核确认（可勾选子集）后**，子代理按最新要素定义执行增量刷新、定稿落盘。
4. 含 mermaid 的刷新文档必须全部 VALID。
5. **审视门**：列出本步实际刷新的资产文档清单（带路径）+ VALID 结论，ask-human 审视通过后才进第 6 步。

## 第 6 步：全链路分析报告（主代理直接产出，收尾必做）

代码生成收口后，由**主代理直接**产出**需求 → 代码全链路分析报告**（报告是事实汇总而非分析，不再派子代理），让人一眼看出改了什么、每处改动对应哪条业务知识与需求条款、引用的资产靠不靠谱。

1. **取证**（主代理汇总各步骤已返回的事实，禁止凭印象）：
   - 测试用例执行结果：第 4 步返回的 DT（测试函数级）与集成（用例步骤级）结果 + 验证命令实跑输出；证据不足时主代理复跑验证命令补证；
   - 业务知识清单：story 业务知识章节 + `docs/0-biz/knowledge/` 已登记条目（K-xxx）+ 需求文档章节 + story 澄清裁定，合并去重（第二、三节共同主键）；
   - 代码修改清单：以 `git diff`（已提交则取本次需求 commit 范围）为唯一事实来源，逐文件核对 story.md 功能点修改清单——清单外改动、清单内未改都要显式暴露；代码与 story 推导表的对照差异在本报告承载，不回填 story.md；
   - 引用资产清单：story「外部文档引用」章节 + 第 4 步实现子代理返回的实际加载文档清单，逐条去重合并；
   - 各步骤返回的冲突偏差、待确认事项（作为资产评估依据，不单独成节）。
2. **撰写三节**（模板见插件 `templates/spec/全链路分析报告模板.md`）：①测试用例执行结果（DT 到测试函数级、集成到用例步骤级）；②代码修改清单（含「业务知识」列）；③变更框图与引用资产质量评估（业务知识主键，与修改清单同口径，重点列缺引用与质量不足）。
3. **落盘**：被分析仓 `docs/1-storys/{功能名}/{YYYYMMDD}-report.md`（归档进本需求的 story 目录，与 story 同目录；次抛件带日期，同日同需求重跑同名覆盖）。
4. **审视门**：报告落盘后，ask-human 审视报告全文；有意见由主代理修订后重新过门，审视通过后流程结束。
5. 评估为「部分符合/不符合」的资产，主代理在回复中显式列出并给出下一步建议（如重跑某 analyze skill、补齐某资产后再生成）。

## 子代理派发通用规则

- prompt 四要素：①加载哪个 skill 全文 ②输入文档/数据路径 ③产出路径与格式 ④返回内容（产出文件清单 + 关键结论 + 待确认清单 + 阻塞项）。
- 无依赖的子代理同一条消息并行派发（第 1 步 4 个分析、第 5 步各资产刷新）；步骤间有依赖严格串行。
- 主代理验收不过关就打回子代理整改，不亲自代写。

## 确认门总表

| 节点 | 询问内容 |
|---|---|
| 第 1 步 | 资产存在→是否刷新；不存在→是否录入（可选子集）；**末：新生成/刷新的资产文档 ask-human 审视门** |
| 第 2 步 | 断点批量 ask-human；审核后是否输出规范设计 md；**末：建模 HTML/设计 md ask-human 审视门** |
| 第 3~3.6 步 | **自动连续执行，不 ask-human**：story 设计 → 3.5 人话改稿（确定性门禁 failures=0）→ 3.6 功能点判读（可推理自修订不问人 / 需人工决策项才 ask-human）|
| 第 3.6 步末 | **story 最终状态 + 判读结果 ask-human 审视门**（功能点总数/全部通过/影响面 grep 全覆盖/mermaid VALID）——全部确认点闭环后才过此门 |
| 第 4 步前 | 是否直接开始实现代码 |
| 第 4 步中 | 需求未明确处澄清（子代理返回待确认清单时） |
| 第 4 步末 | **代码变更 + 测试结果 ask-human 审视门** |
| 第 5 步 | 资产刷新清单审核确认（可勾选子集）；代码是否提交由用户决定；**末：刷新后的资产文档 ask-human 审视门** |
| 第 6 步末 | **全链路分析报告 ask-human 审视门**——审视通过后流程结束 |

## 红线

| 想法 | 现实 |
|---|---|
| "步骤简单，我主代理顺手做了" | 分析/设计/编码/检查一律派子代理，主代理只编排与确认 |
| "这个断点/疑问我补个合理答案" | 所有需求疑问走待确认清单→主代理问用户，不脑补 |
| "设计和代码并行跑省时间" | 步骤间严格串行，确认门不过不进下一步 |
| "story 写完直接判读" | 必须先过 spec-humanize 人话改稿（check_prose.py failures=0）才进 spec-point-verify；但 story→3.5→3.6 自动连续执行，不 ask-human |
| "判读有需修订项就直接进下一步" | 可推理自修订项子代理自行修复重判，需人工决策项 ask-human；全部通过 + 全部待确认项闭环 + ask-human 审视通过才放行进 Step 4 |
| "文档生成了，VALID 也过了，直接进下一步" | 每步校验环节结束固定过 ask-human 审视门——VALID/测试通过只是门的输入，人审视通过才算过门 |
| "代码都测过了，不用再给人看" | 第 4 步末代码变更必须列 diff 摘要 + 测试结果交人审视，通过后才进资产刷新 |
| "报告是收尾交付物，落盘即结束" | 第 6 步报告同样过 ask-human 审视门，审视通过流程才结束 |

| "代码写完直接交付" | 第 5 步资产刷新是收口闸门，docs 不同步需求不算完成 |
| "分析报告凭印象总结一下" | 第 6 步报告的测试结果/修改清单/引用资产评估必须以实跑输出、各步骤返回与 git diff 取证，逐用例逐文件逐篇落实，禁止臆造 |
| "commit 一下方便做 diff" | commit 必须用户明确同意 |

## 与其它 skill 的关系

本 skill 是纯编排层，分别调用：4 个分析 skill（arch-structure-model-analyze、biz-interface-analyze、tech-external-call-guidelines-analyze、tech-framework-guidelines-analyze，第 1 步；全套 14 类资产录入改用 spec-analyze）、spec-function-design-audit（第 2 步）、spec-story-design（第 3 步）、spec-humanize（第 3.5 步，story.md 人话改稿）、spec-point-verify（第 3.6 步，功能点推导链判读循环）、spec-code-generate（第 4 步，代码实现与测试）、spec-update（第 5 步）；第 6 步报告由主代理直接产出；mermaid 验证贯穿各步（mermaid-validate）。各 skill 也可脱离本流程单独触发。
