# 需求/功能设计审核（spec-function-design-audit）

| 输入 | 干什么 | 产出 |
| --- | --- | --- |
| 一篇 Spec/需求/功能设计文档 | 多彩建模 + 七大维度完备性扫描 + ask-human 批量澄清，补齐到可供编码 | 源文档同目录：`{功能名}-建模结果.html`；可选 `{功能名}-功能设计.md` |

**自包含原则**：规则与模板全部归档在自身 references/ 与 assets/ 下（mermaid 验证脚本除外，全插件共用）。

核心思想：把文档翻译成多彩建模图（事件-角色-实体-描述的因果链路），逻辑断裂点在图上自然暴露；同时按七大维度扫描系统设计完备性（表达/功能逻辑/接口/数据模型/非功能约束/设计要素/事实正确性）；全部断点合并为一份清单，统一 ask-human 澄清，产出可供编码人员审核的 HTML。

七阶段，严格按序。

## 阶段 1：解读文档，完成多彩建模

1. 通读文档全文。
2. 按 [references/color-modeling.md](references/color-modeling.md) 提取四类元素：粉「事件」、黄「角色」、绿「实体」、蓝「描述」，按时序/因果连接成链路。不臆造文档中不存在的规则——不确定的标记「待确认」。

## 阶段 2：全面扫描，生成初版 HTML

对照 [references/design-audit-checklist-v2.md](references/design-audit-checklist-v2.md) 七大维度 33 项检查项，按 A→G 顺序扫描。扫描阶段只检出、不提问。

1. **A 表达完备性（全场景必做）**：逐句扫描 A1~A5（句子成分残缺/弱表述·不可测/术语统一/语义无歧义/带病放行门禁）。弱词黑名单：内置词表 ∪ 仓内 `docs/audit/weak-words.txt`（存在则追加）。
2. **B 功能逻辑完备性（全场景必做）**：对照多彩建模图扫描 B1~B7（触发链闭环/角色完备/业务状态机闭环/异常分支含需求与既有行为冲突/边界条件含数据生命周期/跨流程数据衔接/规则定义完整）。
3. **C 接口设计完备性（仅功能设计文档）**：对照功能设计模板 §1.5/§1.6 扫描 C1~C4（对外接口契约/跨服务调用契约/接口权限与安全/OM 接口）。纯需求文档跳过。
4. **D 数据模型完备性（仅功能设计文档）**：扫描 D1~D6（核心实体识别/字段与类型/实体关系/实体状态机/存储介质与生命周期/一致性与事务要求）。纯需求文档跳过。
5. **E 非功能与约束完备性（仅功能设计文档）**：扫描 E1~E6（性能指标/安全要求/可靠性/可维护性/前置依赖/外部约束）。纯需求文档跳过。
6. **F 设计要素完备性（仅功能设计文档）**：扫描 F1~F4（时序图完备/验收用例完备/功能清单完备/用例设计完备）。纯需求文档跳过。
7. **G 事实正确性（全场景必做）**：扫描 G1，检出文档中与通用知识/公开协议标准矛盾的事实性错误（只报有公认标准答案的，须给出权威依据与原文摘录）。
8. **适用场景区分**：纯需求文档（无实现设计章节）检查子集 = A+B+G 共 13 项；功能设计文档（含实现设计章节）检查全集 = A~G 共 33 项。纯需求文档意外涉及 C/D/E/F 维度设计描述时，对应检查项降级为🟡提示级。
9. 复制 [assets/model-template.html](assets/model-template.html)，填入建模结果与全部断点卡片（红色虚线高亮），保存到**源文档所在目录**，文件名 `{功能名}-建模结果.html`。

本阶段只检出、不提问。

## 阶段 3：统一 ask-human 澄清（批量提问循环 + 质量门禁）

1. 断点合并为一份清单，按严重程度排序（🔴 阻塞 → 🟠 风险 → 🟡 提示，分级规则见 design-audit-checklist-v2.md §3.5）。
2. **批量提问**：一次抛出全部问题。每问含编号、原文引用、问题类别、2-4 个具体候选选项（推荐项标注，不提供"其他"兜底）；语义多解类把 N 种理解全部列成选项。**"既有行为是否改造"类断点强制包含"保持现状不动"选项**——当需求未明确要求改造某既有行为时，推荐项应为"保持现状不动"而非"保留但加改造"，避免把改造暗示成默认选择。
3. **核对回答，循环追问**：已裁定的记录「人工裁定+答复时间」；未答/含糊的进下一轮；裁定引入新疑点的重新扫描生成新断点；循环至无新问题。
4. **质量门禁**：全部断点有裁定才进阶段 4。用户跳过或明确带病继续的记「仍存疑」保留红色标记——A 表达完备性仍存疑项须在阶段 5 单独列出"表述问题未清零，不建议进入编码"；B/C/D/E/F 维度仍存疑项按维度列出"XX 维度仍有 N 项未裁定，可能影响编码方向/测试覆盖/数据落地"；G 事实正确性仍存疑项单独列出"事实性错误未确认，存在与公开标准矛盾的风险"。

## 阶段 4：完善 HTML

1. 裁定回填，断点卡片转「已补齐」（绿色边框+裁定内容）；仍存疑项保留醒目标记。
2. 可读性：四色图例置顶；主流程→分支/异常分层；每个元素卡片标注颜色类别、原文出处、确认状态（原文明确/人工补齐/仍存疑）。

## 阶段 5：提醒编码人员审核

最终回复中输出「编码人员审核提醒」：HTML 位置与查看方式、审核要点（已补齐裁定是否符合真实业务、仍存疑项、建模未覆盖的编码细节），并明确提示 **HTML 未经编码人员确认前不得进入编码阶段**。

## 阶段 6：可选输出规范功能设计 md（必须先询问用户）

**必须询问用户**是否按 [references/functional-design-template.md](references/functional-design-template.md) 输出功能设计 md。确认后：

1. 按模板章节生成（功能概述/SR 设计/实现设计/接口设计/安全配置/功能规格/DFX/分配需求）。
2. 内容来源 = 原文档 + 人工裁定；可选章节无内容标"不涉及"裁剪；未覆盖内容标"待确认"，**禁止脑补**。
3. 输出到**源文档所在目录**，文件名 `{功能名}-功能设计.md`。

## 阶段 7：验证产出物中的 mermaid 图（收尾必做）

产出物含 ```mermaid 代码块时，交付前必须逐文件校验：

```bash
node <specgo插件目录>/skills/mermaid-validate/scripts/validate-mermaid.mjs <产出文件...>
```

全部 VALID 才算完成；INVALID 按报错行号修复重验。首次使用先在脚本目录 `npm install`。语法红线见 mermaid-validate skill。

## 输出规范

- HTML 单文件无外部依赖，浏览器直接打开；配色遵循模板内置色板，不改语义。
- 全程用中文输出建模内容、提问与报告；代码标识符与技术术语保留英文。

## 质量检查清单

- [ ] 七大维度扫描全部执行（A 表达/B 功能逻辑/C 接口设计/D 数据模型/E 非功能约束/F 设计要素/G 事实正确性），断点清单分级编号完整；纯需求文档执行 A+B+G 子集
- [ ] ask-human 批量澄清：一次抛出、每问 2-4 个候选、语义多解列全部理解；循环追问至无新问题
- [ ] 全部断点有裁定（或带病记「仍存疑」并单独列出"不建议进入编码"）
- [ ] HTML 落盘源文档同目录，图例置顶、元素标注出处与确认状态
- [ ] 功能设计 md 经用户明确确认才输出；未覆盖内容标"待确认"，无脑补
- [ ] 含 mermaid 产出物全部通过 validate-mermaid.mjs 验证（VALID）

## 关键约束

- **基于实证**：所有检出以实际读到的文档证据为准；引用原文必须真实摘录，禁止目测通过。
- **澄清门禁不可跳**：断点未裁定不进下一阶段，带病继续记「仍存疑」。
- **不修改被审文档正文**：补齐只落在建模 HTML 与可选功能设计 md。
