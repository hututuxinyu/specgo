# spec-point-verify — 功能点推导链判读

编码前唯一门禁。在 story.md 推导表产出（判定列「待判读」）后、代码实现前执行：**逐功能点独立判读 + 一次整体走查**，结果回填同一份 story.md，不另起 point-verify.md。

## 产出物（只回填这四处）

1. **推导表判定列**：「待判读」→ 通过 / 需修订 / 打回设计。
2. **推导表内 `↑影响面核验` 表格行**：每个变更点的推导表底部加一行**表格行**（非 blockquote/散文），写 grep 关键词 + 命中函数数 + 覆盖结论。全覆盖时判定"通过"，有遗漏时判定"需修订"并列出遗漏函数。
3. **需关注事项**：只列有偏差或需知晓的功能点，每条写"结论 + 为什么 + 影响 + 是否影响编码"。全无偏差时写"全部功能点无实质偏差"。
4. **资产缺口汇总**（§6.2，三列表：缺失资产 / 谁来补 / 补什么）：分两类标注，可自动补建型标"spec-update"不阻塞编码，人工提供型标"人工 ask-human"判需修订。无缺口写"无"。

5. **§6.1 判读结果总览**：只记录最终状态（全部通过后的结论），不保留中间修订历程。

无偏差功能点**不逐点展开判读详情**——推导表一行判定即结论。禁止打分附录、分数、评级。

**修订覆盖规则**（铁律）：
- 判读结果**只回填到推导表判定列**（通过/需修订/打回设计 + 一句话理由），不另设章节记录中间偏差；
- 修订后的功能点**直接在推导表原位置覆盖**，不保留"修订前偏差 → 修订后结果"的重复呈现；
- **不设置独立的"判读偏差"章节**——判读结果只存在于推导表判定列 + §6.1 最终结论；

## 判读四问（每个功能点）

1. **推导链成立吗**：定位文档说清"改哪里"，修改指导文档说清"怎么改"，代码落点（文件:函数）与二者一致，中间没有跳跃。
2. **资产真实且支撑吗**：引用的每份文档先 Glob/ls 核实存在，再 Read 核实内容确实支撑推导链中的用途。两步缺一不可，禁止凭文档名判断。
3. **业务意图覆盖吗**：对照需求文档对应章节，功能点行为与需求一致，边界条件无遗漏。
4. **场景必参考齐吗**：按代码落点识别实现场景，对照必参考清单逐类核实。漏引必须分三归因：
   - **功能点漏引**（仓里有这类文档但没引用）→ 判需修订，影响编码正确性；
   - **资产缺口·可自动补建型**（仓里没有文档，但内容可从既有代码/资产事实推导，如 interaction-model 对应流程已在代码中实现）→ 不阻塞，入 §6.2 资产缺口汇总，spec-update 可补建，禁止因此冤枉功能点；
   - **资产缺口·人工提供型**（仓里没有文档，且内容无法从既有代码/资产事实推导——典型：全新外部服务的通信规范、新引入框架的使用指导、第三方平台对接协议）→ 判需修订，返回待确认清单给主代理 ask-human，理由注明"资产属人工提供型，无法从仓内代码/资产推导"。主代理向用户确认：以需求文档对应章节为实现参考准绳，还是先补建资产再实现。

再问一句"**能照着直接写代码吗**"：常量值、边界含不含上限、格式与时区、部署前提等编码必需信息缺失的，列偏差或待确认项。

## 三档判定（死规定，不许自由发挥）

| 判定 | 含义 | 后续 |
|---|---|---|
| 通过 | 四问都成立，可进入编码 | 回填后过审视门 |
| 需修订 | 推导断裂、内容不匹配、意图遗漏、必参考漏引 | 打回设计子代理修订后重判该功能点 |
| 打回设计 | 推导严重不成立或大量漏引 | 打回 spec-story-design 第 5 步重写后重判 |

判定只写三档加人话理由。理由必须指向具体事实（哪份文档哪行、需求哪节、哪个环节断裂），禁止"推导正确"式套话。

## 判读闭环流程（循环直至全部通过）

判读不是一次性动作，而是"判读 → 修订 → 重判"的循环，退出条件是全部功能点"通过"**且待确认项已全部处理**：

1. **逐功能点独立判读**推导链（资产引用真实且支撑、业务意图覆盖、编码信息齐备）；
2. **跨功能点整体走查**（执行顺序自洽、校验先后合理、错误语义一致、编码必需信息齐备）；
3. **三档判定回填**推导表判定列：通过 / 需修订 / 打回设计；
4. **汇总本轮判读产出**，对每个「需修订」项先分类（两轨制）：
   - **可推理自修订**（通过代码/文档事实可推导出唯一正确答案，如：CREATE TABLE IF NOT EXISTS 不改既有表结构须补 ALTER TABLE、删除函数后调用方编译断裂须一并删除、列类型与 entity tag 不一致须对齐等）→ **判读子代理自行修订 story.md 推导表原位置**，不返回主代理 ask-human，修订后直接重判该功能点；
   - **需人工决策**（无法通过代码/文档推理得出唯一答案，含两类：
     - **方案歧义型**：方案 A/B/C 选择、业务策略取舍、逃生通道是否保留等 genuinely ambiguous 决策；
     - **人工提供型资产缺失**：必参考资产不存在且内容无法从仓内代码/资产推导——如全新外部服务的通信规范、新引入框架的使用指导。需用户确认以需求文档为准或先补建资产）→ 返回待确认清单给主代理，主代理 ask-human 澄清；
   - **打回设计**（推导严重不成立或大量漏引）→ 打回 spec-story-design 第 5 步重写后重判；
5. **需人工决策项处理**：
   - 主代理批量 ask-human，用户能确认的 → 答案回传判读子代理，由判读子代理修订 story.md 对应位置（澄清Q&A、推导表等），确认后的项不留痕；
   - 用户确认留到实现时的 → 在推导表对应功能点的代码修改列中标注；
   - 需要外部文档/平台对接的 → 在推导表对应功能点的代码修改列中标注所需文档名称；
6. 修订完成后重判修订过的功能点（走完整四问 + 必参考核实），回到步骤 3（循环）；
7. **循环退出条件**：全部功能点"通过"（0 需修订，0 打回设计）**且全部待确认项已闭环**（确认的已回填到推导表/澄清Q&A、留到实现时的已在推导表标注）。未闭环时循环修复直至闭环，不中途放行。

修订循环中，只重新判读修订过的功能点，未修订的功能点保持原判定。重新判读走完整四问 + 必参考核实，不是只看修订部分。

**两轨制分类原则**：判读子代理对每个「需修订」项判断"是否能通过代码/文档事实推导出唯一正确答案"——能推导则自修订（不 ask-human），不能推导则返回待确认。分类依据必须在返回结果中写明（如"CREATE TABLE IF NOT EXISTS 不改既有表结构，须补 ALTER TABLE，代码事实可推导 → 自修订"或"升级迁移方案 A/B/C 涉及业务策略选择，无法通过代码推理 → 需人工决策"或"external-call-guidelines-fileserver.md 缺失，FileServer 为全新外部服务无既有代码可推导通信规范 → 人工提供型资产缺失，需人工决策"）。

**待确认项闭环原则**：最终文档只呈现闭环状态，不留待确认痕迹。
- 用户已确认给出明确答案的待确认项 → 答案回填到 story.md 对应位置（澄清Q&A表、推导表等），不留"用户已裁定"痕迹；
- 用户确认留到实现时的待确认项 → 在推导表对应功能点的代码修改列中标注"实现时确认"；
- 需要外部文档/平台对接的待确认项 → 在推导表对应功能点的代码修改列中标注所需文档名称；
- 人工提供型资产缺失的待确认项 → 用户确认"以需求文档为准"后，推导表定位/修改指导列填需求文档章节号（如"需求 §3 外部接口设计"），§6.2 资产缺口仍标注"待补建（人工提供型）"供 spec-update 后续补建；
- 最终文档不设独立的"待确认项"章节，所有确认结果融入各自的推导表/澄清Q&A位置。

## 偏差五类

偏差清单的"类型"列只许用这五类，逐条列出，不掩盖：

| 类型 | 定义 |
|---|---|
| 推导断裂 | 环节间逻辑不成立：落点指错层、缺中间环节、定位列为空 |
| 资产虚构 | 引用的文档经核实不存在 |
| 内容不匹配 | 文档存在但内容不支撑推导链中的用途（无相关章节、签名/约束不符、描述过期与澄清结论矛盾） |
| 意图遗漏 | 功能点设计未完整覆盖需求业务意图（模式缺漏、边界条件未体现） |
| 必参考缺失 | 场景必参考类型未被引用，必须注明"功能点漏引"、"资产缺口·可自动补建型"或"资产缺口·人工提供型" |

## 实现场景必参考清单（内置通用模板）

按功能点代码落点识别场景，逐类核实。"典型资产文档"只是命名示例——主代理派发前必须做仓内对表（见流程第 2 步），子代理按实际文档名核对。

| 实现场景 | 识别特征（代码落点） | 必参考文档类型 |
|---|---|---|
| HTTP 接口实现 | controllers/ routers/ handler 函数 | ① 路由注册方式 ② controller 基类与响应结构 ③ 请求/响应数据模型 ④ 错误码体系 ⑤ 交互模型（主链路时序） |
| Service 业务逻辑 | service/ 业务方法 | ① 交互模型 ② 接口契约 ③ 数据模型（读写实体） ④ 并发原语约定（涉锁/channel 时） ⑤ 缓存约定（涉缓存时） ⑥ 错误码体系 |
| DAO 数据访问 | dao/ ORM 方法 | ① 数据模型（表结构与字段约束） ② 数据访问规范（ORM/事务/BaseDao 约定） ③ 实体定义 ④ 并发约定（涉连接池/锁时） |
| 定时任务 | scheduler/ 定时方法 | ① 调度框架使用约定 ② 并发原语 ③ 配置读取方式 ④ 数据访问 ⑤ 告警/日志机制 |
| 缓存读写 | cache 相关文件与方法 | ① 缓存数据结构（生命周期/TTL/容量/清理） ② 并发保护约定 ③ 回源数据访问 ④ 失效策略 |
| 外部服务调用 | remote/ client 方法 / RPC | ① 外部调用规范 ② 韧性策略（超时/重试/熔断降级） ③ 框架客户端使用 ④ 错误处理约定 |

判定规则：同一类型引用该类别任一文档即算已引用；"不需要（语言基础能力）"的指导文档不替代必参考类型；仓内无对应类别文档时区分"资产缺口·可自动补建型"（内容可从代码推导，不阻塞）与"资产缺口·人工提供型"（内容无法从代码推导，判需修订并 ask-human）。

## 工作流程

### 第 1 步：提取功能点清单

读 story.md，遍历每个变更点的功能点拆分表与推导表，提取：功能点描述、所属变更点功能描述、推导链行（定位文档/修改指导文档/代码落点/判定列应为「待判读」）。

### 第 2 步：仓内资产对表（主代理做，派发前必做）

Glob `docs/0-*/*.md` 列出仓内资产文档，按必参考类型归类，把**实际文档名清单**塞进子代理 prompt——通用模板变成这个仓的类别检查表，子代理不用自己 Glob 猜文档名。

### 第 3 步：逐功能点派发判读子代理

一个子代理只判一个功能点，同一条消息并行派发；超过 10 个分批，每批 ≤10，批间不传中间结果。

prompt 只塞四块，**不塞 skill 全文**：①任务一句话 ②判读四问（含归因要求）③偏差五类 ④返回格式。另附：该功能点上下文（描述 + 推导链行）、仓内资产清单、需求文档路径。

子代理返回格式（单功能点判读）：

```
功能点：<描述>
判定：通过 / 需修订 / 打回设计
理由：<人话，四问各自的结论与依据，资产核到文档行号、需求核到章节>
偏差清单：<逐条：偏差描述 | 五类之一（必参考缺失注明漏引/缺口）| 是否影响编码；无偏差写"无偏差">
待确认项：<无法判定、需用户拍板的疑问，没有写"无">
修订建议：<判定为需修订/打回设计时必填：修订哪个功能点、怎么改、需要用户澄清什么；通过时写"无">
```

**主代理每轮判读后返回格式**（汇总所有子代理结果 + 整体走查，给 specgo 编排层或用户）：

```
判定统计：通过 N / 需修订 M / 打回设计 K（共 N+M+K 个功能点）
功能点判定明细：
  - <功能点描述>：<判定> — <一句话理由>
  ...
需修订项修订建议：
  - <功能点>：怎么改 + 需用户澄清什么（逐条列；全部通过时写"无"）
跨功能点整体走查结论：<自洽/顺序矛盾/错误语义不一致等，发现的问题逐条列；无问题写"无矛盾">
判定列回填状态：已回填 / 待回填（注明原因）
```

### 第 4 步：主代理验收

- 四问都有依据，资产核实写明"存在/不存在 + 支撑/不支撑"，需求覆盖核到章节；
- 偏差分类合规，必参考缺失已区分漏引与缺口，扣结论的必须是"漏引"而非"缺口"；
- 无偏差写"无偏差"而非空白。
不合格打回该子代理（续会话）补正。

### 第 5 步：影响面扫描（grep 兜底，防漏行）

逐点判读只验证已有行，不查漏掉的行。这一步 grep 受影响文件，把所有触及变更概念的函数拉出来，逐个对照推导表——有对应行的正常，没对应行的标遗漏。

**怎么扫**：

对每个变更点，根据推导表"代码修改"列涉及的文件和概念关键词，执行 grep。关键词从变更点的功能描述和代码修改内容中提取（如缓存键变更 → grep "cache\|IMEICache"，导入流程 → grep "Import\|parseCSV\|importLock"）。

**对照规则**：

grep 命中的每个函数，在推导表功能点列中找对应行：
- 找到对应行 → 已覆盖
- 没找到对应行，但该函数确实不需要改 → 标"不变"
- 没找到对应行，且该函数需要改 → **遗漏**

**回填格式**（推导表内表格行，铁律）：

**格式铁律**：影响面核验必须是推导表内的表格行，禁止用 blockquote、散文段落或独立小节。grep 输出精简为"关键词 → N函数命中(函数:行号) 全覆盖/遗漏X"，不贴完整命令与冗长描述。

全覆盖时：
```
| ↑影响面核验 | grep "cache\|IMEICache" auth_service.go → 5 函数全覆盖 | — | — | 通过 |
```

有遗漏时：
```
| ↑影响面核验 | grep "cache\|IMEICache" auth_service.go → 命中 6 函数，遗漏 cleanCacheImpl | — | — | 需修订 |
```

**遗漏处理**：

遗漏函数不能只停在扫描行里——补为正式功能点行（加入功能点拆分表 + 推导表），走完整四问判读。补入后扫描行更新为全覆盖：

```
| #3 cleanCacheImpl 淘汰删除键 | ... | ... | ... | 通过 |  ← 补入的正式行
| ↑影响面核验 | grep "cache\|IMEICache" auth_service.go → 6 函数全覆盖（含补入 #3） | — | — | 通过 |
```

**注意**：grep 按文件×概念维度扫描，一个变更点可能涉及多个文件，每个文件单独 grep 后合并命中函数集。全覆盖时也留痕（证明扫过），不只写"无遗漏"。

### 第 6 步：整体走查（必做，逐点判读替代不了）

逐点判读是隔离的，**跨功能点的矛盾只有通读全文才能发现**。主代理（或派一个整体走查子代理）通读 story.md 全文，检查：

1. **端到端顺序自洽**：把各变更点串成一条执行链走一遍。同一动作只在一个阶段做；先后依赖无矛盾——例如"数有效行数"依赖"先解析"，若文档写"锁外预检行数、锁内才解析"，必须说清解析做几次、各做什么，否则就是顺序矛盾。
2. **廉价校验在前**：参数、规格类校验应先于拿锁、开事务等资源竞争；有例外必须写明理由。
3. **错误语义一致且对调用方可理解**：同类问题同类错误码；"进行中冲突"报成"参数错误"这类误导性归属，列待确认项让用户拍板。
4. **编码必需信息齐备**：常量值、边界含不含上限、格式与时区、部署前提（如多实例下进程内锁失效、无数据库约束兜底）都已写明。
5. **验证方式可执行**：确切命令与路径，无"如存在则执行"。

走查发现的问题按偏差五类处理，需用户拍板的进待确认清单。

### 第 7 步：回填与一致性自检

按"产出物"三处回填，然后对照 specgo 文档约定做一致性自检：

- 无「待判读」等占位残留；
- 修订已在推导表原位置覆盖（不保留修订前偏差痕迹），需关注事项与缺口汇总结论与最新判定一致；
- 数量算得平：功能点总数 = 通过 + 需修订 + 打回之和，需关注事项条数与总览吻合；
- 全文无分数、无失效交叉引用；
- "定位/指导文档"列口径统一：文档名 / 不需要（理由）/ 缺失（资产缺口），无留空。

### 第 8 步：ask-human 审视门

主代理展示三样，缺一不可：

1. 判定总览：每个功能点一行——判定 + 一句理由；
2. 需修订/打回清单（如有）：主要偏差类型 + 一句话原因；
3. 影响编码的偏差条目（含整体走查发现的）。

待确认项去重后一并提交用户确认，确认结果回填到需关注事项对应条目。用 AskUserQuestion 询问是否审视通过：

- 全部通过 + 用户审视通过 → 判读闭环结束，进入代码实现；
- 有需修订项 → 进入"判读闭环流程"修订循环：打回设计子代理修订推导表原位置后重判修订过的功能点，重新过门；
- 有打回设计项 → 进入"判读闭环流程"修订循环：打回 spec-story-design 第 5 步重写后重判，重新过门。

循环退出条件见"判读闭环流程"：全部功能点"通过"，0 需修订，0 打回设计。

## 子代理判读纪律

1. 只看分配给它的一个功能点，不越界；
2. 资产必须"存在 + 内容支撑"两步核实，这是与设计自评的核心差异；
3. 必参考逐类核实，漏引必须注明归因；
4. 证据到文档行号、需求章节号，禁止泛泛而谈；
5. 偏差逐条列出按五类标注，不掩盖、不自行判断"不严重就不列"；
6. 不脑补：无法判定的进待确认项；
7. 两轨制修订：可推理自修订的"需修订"项判读子代理自行修订 story.md 推导表原位置（不 ask-human），需人工决策的返回待确认清单给主代理；"通过"项只判不修；
8. 修订覆盖：设计子代理修订推导表时在原功能点行原位置覆盖，不另起偏差章节、不保留修订前 → 修订后重复。

## 红线

| 想法 | 现实 |
|---|---|
| "功能点太多，一个子代理全包" | 逐功能点独立子代理并行，保证隔离与深度 |
| "设计自评过了，判读走个过场" | 判定只来自独立判读，设计侧一律「待判读」 |
| "文档名看着像真的就不核了" | 存在 + 内容两步核实，缺一不可 |
| "逐点都过了，不用整体走查" | 顺序矛盾、口径冲突只有整体走查能发现，必做 |
| "仓里没文档，算功能点漏引" | 资产缺口不冤枉功能点，归因必须分清 |
| "偏差不严重就不列" | 偏差全列，影响由主代理与用户判断 |
| "判读顺手把推导链修了" | 只判不修适用于"通过"项；可推理自修订的"需修订"项判读子代理自行修订推导表原位置（两轨制），需人工决策的才返回待确认 |
| "改完一处就回填" | 修订同步所有位置，过一致性自检 |
| "审视门走个过场" | 人审视通过才算过门 |
| "打个分显得严谨" | 只写三档判定加人话理由，禁止分数与打分附录 |
| "另起 point-verify.md" | 回填同一份 story.md，不另起文档 |
| "判完一轮就放行" | 必须循环到全部通过才放行，见"判读闭环流程" |
| "修订偏差另起章节记录" | 原位置覆盖，不保留修订前 → 修订后重复呈现 |
| "仓里没文档，算资产缺口不阻塞" | 资产缺口须分两类：可自动补建型不阻塞；人工提供型（全新外部服务/新框架等无法从代码推导）判需修订并 ask-human 确认 |
| "影响面核验用引用块/散文写" | 必须为推导表内表格行，grep 输出精简为关键词+命中数+覆盖结论，禁止 blockquote/散文段落 |

## 与其它 skill 的关系

- specgo（主流程）：本 skill 是其第 3.6 步，由其调度；文档结构与写作要求遵循 specgo 的 story.md 文档约定。
- spec-story-design：前置，产出判定列「待判读」的推导表；判读不过的功能点打回其第 5 步。
- spec-code-generate：后继，判读通过 + 审视门通过后才允许编码。
- specgo 第 4 步：以本步回填的判定为编码基线；代码与判定的对照差异归 specgo 第 6 步全链路分析报告承载，不回填 story.md。

## 单独触发模式

已有 story.md（判定列「待判读」）时可脱离 specgo 单独触发：输入 = story.md 路径 + 需求文档路径；产出 = 回填同一份文档（判定列 + 需关注事项 + 资产缺口汇总）；流程同第 1-8 步，含判读闭环循环。
